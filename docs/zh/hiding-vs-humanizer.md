# /hide 与 humanizer：内容泄露与文体指纹

`/hide` 让用户控制文件暴露的内容，humanizer 调整文体特征。它们的目标和操作边界不同。本文对比两者的定位差异，并说明 `/hide` 的能力边界。

对比对象是 [blader/humanizer](https://github.com/blader/humanizer) 及其衍生版本（如中文译版 humanizer-zh），基于 Wikipedia [Signs of AI writing](https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing) 页面整理的 AI 写作特征指南。

## 一句话定位

> **/hide 管"内容说漏"，humanizer 管"腔调露馅"。**

- `/hide` 处理**语义泄露和用户指定的敏感内容**：文件里出现了不该出现的凭据、规则引用、思维推导过程、AI 自我指涉，或用户明确要隐藏的数据来源、内部规则等内容。
- humanizer 处理**文体指纹**：内容本身没问题，但表达方式带有 AI 的统计特征——破折号过度使用、三段式列举、"此外/彰显/格局"等高频 AI 词汇、以 -ing 结尾的肤浅分析、宣传腔。这些是 AI 检测器（GPTZero 类）赖以工作的信号。

一个文件可以通过 `/hide` 清理后不含任何语义泄露，但文风仍然一眼 AI；也可以经 humanizer 改写后文风自然，但仍然在注释里写着"根据 skill 指示..."。两者叠加才构成完整的"像人写的"。

## 维度对比

| 维度 | /hide | humanizer |
|------|---------|-----------|
| 解决什么 | 语义泄露：说了不该说的 | 文体指纹：说话方式像 AI |
| 操作对象 | 文件（代码、配置、Markdown、文档） | 文本（文章、prose） |
| 操作方式 | 删除选中的注释和正文；配置凭据仅允许格式安全占位符；保留可执行代码 | **重写**——重构句式、变换节奏、注入个人语气 |
| 输出行为 | 默认静默；预览、会话选择、告警、错误和必要确认可见 | 改写文 + 变更总结（部分版本附评分） |
| 安全层 | 凭据与密钥剥离 + 强制轮换警告 | 无——完全不涉及 secrets |
| 交互控制 | 自然语言意图、HITL、预览、三种输出模式、可选新上下文子代理 | 无流程控制，纯类别指南 |
| 结构保障 | JSON/YAML/XML 在解析器可用时校验；缺失时允许目视回退，不保证行为不变 | 取决于具体工具 |
| 类别依据 | 自定义原则（判断式，明确反对关键词 grep） | WikiProject AI Cleanup 实证观察（词表式，接近可 grep） |

## 唯一的重叠区

`/hide` 的 AI 自我指涉与 humanizer 的"协作交流痕迹"、"谄媚语气"两类内容覆盖同一批内容：

> "Here's the result:"、"希望这对您有帮助！"、"Great question!"、"Let me know if..."

处理方式不同：`/hide` 直接删除（这些句子在文件中没有存在价值）；humanizer 改写为正文（它假设周围还有需要保留的 prose）。对代码注释和配置文件，删除是正确动作；对文章正文，改写是正确动作。重叠区的分工其实也是按操作对象划分的。

## 为什么 /hide 不做文体人性化

`/hide` 的核心原则之一是**清理内容，不做人性化改写**。它保留可执行代码、字符串和运行时可见文档字符串；配置凭据仅允许格式安全占位符。文体人性化则需要重构句式、替换词汇、调整节奏：

1. **修改需要验证**。删除和改写都可能影响含义，具有工具语义的注释也可能影响执行。`/hide` 优先处理允许编辑的内容，结构校验失败时保留原文件；重要文件仍需项目自身的测试。
2. **交互由工作流决定**。`/hide` 的默认静默不取消用户控制：Session 清理需要选择，整文件删除需要明确确认，预览和安全告警也会输出。
3. **文体问题有专门工具**。与其在 `/hide` 里内置一个降级版 humanizer，不如保持边界清晰，推荐链式使用。

## 按需组合

只有用户另外需要调整 Markdown 文风时，才考虑组合两个独立工具：

```
/hide 清理 doc.md       # 第一步：剥离语义泄露（凭据、规则引用、推导过程、自指涉）
<humanizer> doc.md      # 第二步：改写残余的 AI 文体（破折号、三段式、AI 词汇）
```

顺序重要：先 `/hide` 后 humanizer。反过来的话，humanizer 可能把"我们按照 AGENTS.md 的约定选择了 X"改写成更自然的"按团队约定选择了 X"——文体变好了，但未共享规则引用还在，且变得更难识别。

对纯代码文件，通常只需要 `/hide`——代码注释被剥离后剩下的是可执行代码，不存在文体问题。

## 能力边界声明

`/hide` 的内容清理不承诺文件看起来由人类编写，也不保证通过 AI 检测：

- **覆盖**：内容级痕迹和用户通过自然语言指定的敏感内容。
- **不覆盖**：文体级特征。Markdown 文档的行文风格、词汇选择、句式节奏不在 `/hide` 的处理范围内。若文档需要通过 AI 文体检测或面向对文风敏感的读者，应在 `/hide` 之后叠加 humanizer 类工具。

## 互相借鉴的方向

**`/hide` 可以向 humanizer 借鉴：**

- 类别依据的外部背书。humanizer 引用 Wikipedia 的实证观察数据；`/hide` 的五类内容类别是自定义原则，补充外部参照（AI 检测研究、真实泄露案例）能增强可信度。

**humanizer 类工具可以向 `/hide` 借鉴：**

- 安全层。humanizer 完全不检查 secrets——一篇待"人性化"的文章里若含内部 URL 或 token，会被原样保留甚至改写得更隐蔽。
- 工程化。自然语言交互、预览、输出模式、版本管理与 CI，humanizer 类工具普遍缺失。
- 结构校验。改写比删除风险更高，却没有任何 post-hoc 验证。

## 结论

| | 内容干净 | 内容泄露 |
|---|---|---|
| **文风自然** | 目标状态 | 只跑了 humanizer |
| **文风 AI** | 只跑了 /hide | 原始输出 |

`/hide` 与 humanizer 不是竞品，是相邻两层防线。`/hide` 选择把边界画在"只删不改写"上，代价是放弃文体层，收益是静默、安全、结构可验证。文体层交给专门工具，链式使用。
