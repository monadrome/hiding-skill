# 设计取舍：事后清理而非实时约束

## 问题

AI 编码助手生成的文件可能携带"泄露痕迹"——AI 自指涉（"Here's the result:"）、临时尝试记录、规则与约束引用（"按照 AGENTS.md 的约定..."）等。这些内容会让后续读者推断文件的来源、生成过程、AI 参与和内部约束，甚至暴露安全信息。面向读者的长期技术理由，例如"we chose X because Y"，本身不是泄露，应予保留。

面对这个问题，有两种策略：

- **策略 A（实时约束）**：在每会话中注入规则，要求模型在生成时主动避免泄露。
- **策略 B（事后清理）**：模型自由生成，用户需要时运行清理命令（`/hide`）统一剥离。

`/hide` 选择了策略 B。本文解释为什么。

## 实时约束的隐性代价

### 1. 指令遵循与推理能力的损耗

以始终开启的规则文件为例（~400 tokens），注入到每会话的上下文中：

```markdown
Before committing, pushing, or sharing files, scan them for AI-generated artifacts.
- Don't say "As an AI", "I think", "Here's the result"
- Don't include reasoning trails in comments
- Don't reference AGENTS.md or skill instructions
...
```

这 ~400 tokens 不是"提醒"——是**约束**。模型每次生成输出时，都需要在约束条件间做额外判断：

- "用户让我解释设计思路，规则却说不要写推导过程——我怎么表达？"
- "这是一个 code review 场景，说'I think'是自然的——会被标记吗？"
- "TODO 标记是团队约定还是 AI 自言自语？"

这些额外约束可能增加判断负担；实际对推理质量的影响取决于模型和任务，仓库尚无对照测量。

### 2. 防线不完整：规则注入不能替代清理

即使注入了规则，模型仍然会泄露：

- AI 自指涉太自然了——"Let me..."、"Here's..." 是人类和 AI 都用的表达，模型做不到 100% 准确区分
- 推理链条有时是正确的输出——用户确实需要知道"为什么选 X 而不是 Y"，但格式上暴露了 AI 思考过程
- 约束之间会冲突——"保持简洁"和"解释清楚"和"不写 AI 痕迹"三者互斥

因此，生成时的规则不能保证最终文件符合用户的内容边界；需要时仍可独立检查文件。事后清理也可能漏检或误判，不保证覆盖率更高。

### 3. 输出质量的悖论

最微妙的问题：实时约束会让模型输出变得"不自然"——刻意回避某些短语、句式生硬、回避合理的解释。这种不自然本身就是一种 AI 痕迹。

事后清理将内容筛选与生成分开，但不保证产物看起来由人类编写，也不消除文体特征。`/hide` 的目标是让用户控制文件暴露的内容。

这正是 `/hide` 静默执行哲学成立的前提：

> after `/hide` runs, the selected file contains no sign that it ran

如果模型在生成时就已经被规则扭曲了，那"静默"没有意义——文件从一开始就带着"被约束过"的痕迹。

## 事后清理的优势

### 1. 减少常驻约束

普通会话不常驻加载清理规则；用户调用 `/hide` 时才加载相应指令。调用本身仍有上下文和执行成本，实际效果需要在目标 Agent 中测量。

### 2. 独立检查产物

文件完成后，可以按 Step 0-4 检查：校验输入 → 扫描凭据 → 判断整文件删除候选 → 移除允许编辑的内容 → 验证候选版本。结构校验不能证明语义和执行行为不变；重要文件仍需项目自身的测试。

Step 2 的整文件判断不采用百分比阈值：只有假想移除临时痕迹和符合自动清理条件的用户目标匹配后，不再留下有用的独立参考内容，才建议删除；模糊匹配必须保留。预览只报告候选；实际删除始终需要用户明确确认。

### 3. 用户可选择、可控制

不是每个场景都需要清理。探索性编码、内部讨论、临时文件可以保留过程痕迹；当用户希望文件减少对来源、过程、AI 参与、约束或敏感上下文的暴露时，再运行 `/hide`。提交、推送、分享前只是常见场景。

HITL（Human-in-the-Loop）模式更进一步：无参数运行 `/hide` 时，它分析当前 session 中通过文件编辑工具创建或修改的文件，列出泄露候选项，让用户选择处理哪些。控制权始终在用户手中。

### 4. 哲学一致性

`/hide` 的静默执行约束要求**不在产物中留下清理标记**，也不输出逐项清理总结。成功写入后仅报告实际修改/创建的文件路径和验证通过状态；预览、会话发现与选择、凭据告警、错误和必要确认也属于显式例外。这不意味着改写工具记录、Git 历史或其他外部记录。

## 代价与权衡

选择了事后清理，意味着：

- **用户需要记住运行命令**——这是最大的劣势。实时规则不需要用户操作。对策：将 `/hide` 融入需要控制文件暴露面的工作流，例如审查、交接、归档、发布或 `git commit` 前。不注入会话提醒——任何提醒本质上都是约束，与事后清理哲学矛盾。

- **不能替代安全意识**——机密泄露在事后清理时已造成损失。用户不应依赖任何事后工具来管理凭证——密钥管理应使用环境变量和密钥管理器。`/hide` 的凭据清理是最后一道防线，不是第一道。

- **大文件有性能开销**——Step 0 限制文件大小。超大文件需要分批处理。

## 总结

| 维度 | 实时约束 | 事后清理 |
|------|---------|---------|
| 指令加载 | 生成时持续考虑额外规则 | 用户调用时加载清理规则 |
| 文体影响 | 可能约束生成表达 | 不做人性化改写 |
| 检查时点 | 生成阶段自检 | 文件完成后扫描，仍可能漏检或误判 |
| 用户控制 | 被动（每会话生效） | 主动（需要时调用） |
| 是否需要额外操作 | 否 | 是 |
| 产物标记 | 由具体规则决定 | 不添加清理标记；必要交互仍可见 |

`/hide` 选择了事后清理，因为它的目标不是改变模型的行为，而是让用户控制文件最终暴露的内容。好的工具不该教模型怎么说话——它应该让模型自由说话，然后在需要的时候，无声地擦掉用户不想留下的痕迹。
